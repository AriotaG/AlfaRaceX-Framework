# Audit tecnico AlfaRaceX — 25 settembre 2026

## Esito e perimetro

**PARTIAL SOFTWARE VERIFICATION — HARDWARE VALIDATION REQUIRED.**

evidenze la qualifica SOFTWARE VERIFIED dell'intero prodotto, né HARDWARE VERIFIED.
Le correzioni sono una candidata di audit Desktop `0.1.1-audit.1`.

Baseline ufficiale: `AriotaG/AlfaRaceX-Framework`, main
`c7e6a11b2d96b43259b0de0e96ba427d56c6c257`. Checkout iniziale pulito;
lavorazione separata su `audit/validation-2026-09-25`.
Le release trovate comprendono firmware `1.0.0-rc5` e Desktop `desktop-v0.1.0`.

I firmware pubblicati non sono stati sostituiti durante questo audit.

## Struttura esaminata

- `include/arx`, `src/core`, `src/features`: core C portabile, CAN, ISO-TP,
  link tra controller, configurazioni e funzioni veicolo.
- `targets/stm32f072_common`: entry point embedded `src/main.c`, HAL, USB,
  GPIO/UART, linker distinti C1 e C2/BH, pagine persistenti.
- `desktop/AlfaRaceX.Desktop`: entry point `App.Main`, WPF, WebView2, bridge,
  SQLite, log, UI locale. Sidebar con le sei viste richieste.
- `updater/AlfaRaceX.Updater`: implementazione C# condivisa di HEX, manifest,
  enumerazione SetupAPI, WinUSB, DFU, backup e ripristino; frontend legacy.
- `distribution`, `.github/workflows`, `tools`, `tests`, `docs`: manifest,
  packaging Velopack, CI host/ARM, test e documentazione.

Il recupero del contesto include gli estratti accessibili dei task precedenti su
backup BACCAble, Desktop, UI/disclaimer, ELM, manuale e infotainment. Non è stato
possibile certificare il recupero integrale di ogni conversazione e di ogni dump.
Le dichiarazioni storiche di completamento non sono utilizzate come risultati di test.

## Fonti e conflitti

Manuale fornito **BACCABLE OBD V4.7, 31/08/2026, 47 pagine**: testo estratto dal PDF
locale e confronto con la copia documentale. Riferimenti principali: §1.11 per PROG,
driver e aggiornamento; §2.1 per RES/DISTANCE sul volante; §2.32 per ELM su C1.
Il pulsante PROG fisico non va confuso con RES sul volante. Pressioni brevi/lunghe
di altri pulsanti fisici non sono state dimostrate.

La modalità ELM documentata usa C1, MAIN SETUP e SAVE&EXIT; dopo dieci secondi senza
USB torna alla modalità normale. Il manuale descrive anche possibili interferenze
con immobilizer. Questo è un requisito documentale, non un test superato da ARX.

Il manuale marca Remote Start e Pedal Booster come in sviluppo; p.22 include anche
READ FAULTS tra le funzioni da non abilitare, mentre §2.18 ne descrive l'uso sul Body.
La contraddizione rimane aperta: non promuovere READ FAULTS a funzione fisicamente
validata senza identificare versione firmware e prova corrispondente.

Documento fornito **Come aggirare il blocco SGW.pdf** e manuale §1.1/1.8: distinguono
presa diagnostica protetta e connessioni sul lato reti veicolo. Non provano la
topologia effettiva della Stelvio MY20 dell'utente. Nessun bypass automatico o
modifica PROXY è stato eseguito. TFT e widget infotainment nativo restano distinti.

Il master `BACCAble_Backup_FULL_ORIGINAL.zip` e il relativo checksum sono stati
individuati nell'archivio documentale. Il download dei byte ha restituito HTTP 403.
**Hash del master non ricalcolato, contenuto non confrontato, master non modificato.**
Non si attribuisce VERIFIED AGAINST BACCAble a test che usano solo vettori ARX.

## Difetti corretti

| Area | Difetto / rischio | Correzione ed evidenza |
|---|---|---|
| Intel HEX | EOF mancante, record dopo EOF, duplicati, overflow e record di controllo malformati accettati | Parsing rigoroso; sette test negativi fallivano prima della correzione; dieci casi HEX ora passano |
| Manifest | Ruoli duplicati, limiti Flash e URL non vincolati al pacchetto atteso | Tre ruoli univoci, prodotto/versione, SHA-256, URL HTTPS ufficiale e corrispondenza versione/ruolo; test negativi |
| Download | File temporaneo riutilizzabile, dimensione non limitata e corpo HTTP senza deadline complessiva | Nome univoco, massimo 1 MiB, deadline di due minuti, eliminazione download parziali; test bytes/hash/dimensione con fixture HTTP |
| SetupAPI x64 | Offset DevicePath usava la dimensione allineata della struttura | Offset WCHAR dopo DWORD (4 byte), cbSize distinto, controllo buffer; compilato, enumerazione fisica da provare |
| DFU | Fallback arbitrario transfer size, trasferimenti corti non sempre rifiutati, polling poco diagnosticabile | Descrittori obbligatori, lunghezze esatte, stati e timeout controllati, cancellazione tra trasferimenti, cleanup su apertura fallita |
| Backup | Nomi collidenti e assenza di verifica del file scritto | CreateNew, UTC + GUID, flush su disco, rilettura SHA-256, metadati con portata e limite dell'identificazione |
| Restore | Metadati facoltativi permettevano di fidarsi del nome file | Metadati obbligatori, prodotto/data/nome/ruolo/mappa/hash; catalogo verificato prima del restore Desktop |
| Prima di scrivere | Flash/restore non conservavano sempre una copia preventiva | Backup automatico prima delle due operazioni; confronto DevicePath e hash Flash prima dell'erase. Non è autenticazione del ruolo MCU |
| Uscita DFU | IOException descritta come disconnessione riuscita | Log distingue memoria verificata da riavvio non confermato, conservando l'errore |
| Bridge WPF | Callback DFU poteva accedere a WebView2 da worker thread | Dispatch sulla UI, origine HTTPS locale verificata, diagnostica ProcessFailed e OS |
| UI | Pulsanti restavano disabilitati dopo preparazione; etichette ambigue | Ricalcolo stato pulsanti; SHA-256 OK e firmware disponibile; backup descritto come Flash interna |
| ISO-TP | Payload oltre 255 byte troncato, segmenti di altre sorgenti mescolabili, CF corti accettati | Rifiuto lunghezze non valide; binding bus/ID/formato del ricevitore; CF completi; regressione riprodotta prima e corretta |
| Primo avvio embedded | Immobilizer, Smart Start/Stop e Clear DTC attivi su memoria vuota | Disattivati nei default; valori legacy espliciti conservati; test configurazione/storage passano |
| Packaging | Risorse Bootstrap dipendenti da preparazione esterna; pubblicazione sovrascrivibile | Bootstrap 5.3.8 e licenza versionati; versione da csproj; WebView2 richiesto; release solo esplicita, draft/prerelease, nessun clobber |

La modifica dei default è deliberatamente diversa dal default immobilizer del manuale:
una configurazione vuota non abilita interventi non validati. Non riscrive scelte
salvate. Il solo flag seatbelt mantiene l'allarme abilitato; non si dichiara per questo
la totale passività CAN del firmware, che richiede ancora verifica del traffico.

## Problemi bloccanti ancora aperti

1. **Ruolo MCU non autenticato.** VID/PID DFU e selezione BH/C2/C1 non dimostrano la
   porta fisica. I controlli sui nomi/hash impediscono errori documentali, non il
   cross-flash su un'altra MCU identica. Serve identità attestata o confronto con
   backup originali classificati e una procedura di associazione verificata.
2. **Mappa fisica non confermata.** `hardware.json` nomina C8-compatible; linker e
   backup assumono 128 KiB. C1 usa una regione da 96 KiB, C2/BH da 60 KiB; dati a
   0x0801E000/1E800/1F000/1F800. Nessuna riscrittura delle mappe per supposizione:
   occorre confermare capacità, protezioni e pagine di ogni MCU prima di scrivere.
3. **DFU end-to-end non provato.** Driver, descrittori, cancel/disconnect, erase,
   verifica, uscita e recovery richiedono banco fisico. Un SHA di backup non prova
   capacità Flash, protezioni o validità di OTP/option bytes, esclusi dal backup.
4. **UI e installer non qualificati.** Primo avvio reale bloccato localmente;
   installazione pulita, reinstallazione, disinstallazione, upgrade e conservazione
   dei dati devono passare su Windows isolato. Setup non firmato.
5. **Parità BACCAble non dimostrata.** Master non leggibile, nessun replay comparativo
   acquisito; baud/pin/framing del repository restano implementazioni da confermare.
6. **Gestione aggiornamenti incompleta.** Bootstrap Velopack e packaging non sono
   un UpdateManager operativo; downgrade/rollback applicativi e recovery transazionale
   dopo crash durante Flash non sono dimostrati. Nessun journal persistente di
   operazione incompleta implementato in questa candidata.
7. **Copertura negativa parziale.** Mancano prove di timeout seriale/USB reali, errori
   CAN, permessi insufficienti completi, assenza WebView2, disconnessioni e perdita
   alimentazione. Non equiparare i test metadata a test di restore fisico.
8. **Build firmware riproducibile ancora aperta.** CI STM32CubeF0 segue il ramo remoto;
   toolchain ARM e dipendenze devono essere fissate e i tre binari ricostruiti e
   confrontati. I test portabili non sostituiscono il link ARM.

## Riproduzione software

Da checkout pulito su Windows con SDK .NET 8, CMake e compilatore C disponibili:

```powershell
dotnet run --project tests/AlfaRaceX.HostTests -c Release
dotnet restore desktop/AlfaRaceX.Desktop
dotnet build desktop/AlfaRaceX.Desktop -c Release --no-restore
dotnet publish desktop/AlfaRaceX.Desktop -c Release -r win-x64 --self-contained true --no-restore -o publish
cmake -S . -B build -DARX_STRICT_WARNINGS=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
dotnet tool install -g vpk --version 1.2.0
vpk pack --packId AlfaRaceX.Desktop --packVersion 0.1.1-audit.1 --packDir publish --mainExe AlfaRaceX.exe --packTitle AlfaRaceX --framework webview2
```

Eseguire separatamente `AlfaRaceX.exe --smoke-test` e `--ui-smoke-test`, verificando
il codice di uscita e i log. Entrambi usano dati temporanei, non il catalogo reale.
La pipeline Desktop automatizza anche il test dell'eseguibile installato.
